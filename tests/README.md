# Автотесты

Проверяются реальные обработчики FastAPI, SQL-запросы репозиториев, авторизация,
валидация, обработка изображений и жизненный цикл приложения.
По просьбе владельца проекта код приложения не менялся. Подтверждённые дефекты
отмечены строгими `xfail`, а ожидаемое правильное поведение описано в самих тестах.

## Установка и запуск

Из корня проекта, с активным виртуальным окружением:

```powershell
python -m pip install -r requirements-test.txt
python -m pytest
```

Без активации окружения на Windows:

```powershell
.venv\Scripts\python.exe -m pytest -q
```

Быстрые тесты без PostgreSQL, Redis и Celery worker:

```powershell
python -m pytest tests/unit_tests -q
# Или через маркер:
python -m pytest -m unit -q
```

Интеграционные проверки с настоящей PostgreSQL:

```powershell
python -m pytest -m integration -q
python -m pytest tests/integration_tests/bookings -q
```

Подробности известных ошибок и отдельный тест:

```powershell
python -m pytest -rx --tb=short
python -m pytest tests/integration_tests/bookings/test_booking_api.py::test_add_booking -v
```

Чтобы получить отчёт для CI, используйте встроенную возможность pytest:
`python -m pytest --junitxml=pytest-results.xml`.

## Тестовая конфигурация и данные

Скопируйте `.env-test.example` в `.env-test`, если тестовый файл ещё не создан,
и укажите доступ к **отдельной тестовой базе PostgreSQL**. Существующая
`.env-test` не изменяется. База должна существовать; пользователю БД нужны права
создавать и удалять схемы и создавать таблицы в них.

Тестовый файл загружается явно через python-dotenv; установленные переменные
окружения имеют приоритет. Автозагрузка рабочего `.env` плагином pytest-dotenv
отключена. Для unit-тестов есть безопасные значения по умолчанию, поэтому им
не нужны файлы с секретами и работающие сервисы. Интеграционные фикстуры
отказываются подключаться, если `MODE != TEST`. Секреты из `.env-test` в Git
добавлять не нужно; пример содержит только тестовые значения.

В начале интеграционного запуска создаётся случайная схема
`pytest_<uuid>`. Подключения тестов используют только её через `search_path`.
Существующие таблицы базы не пересоздаются и не очищаются. В конце удаляется
только схема текущего запуска.

Каждый тест выполняется в отдельной внешней транзакции. Сессии репозиториев
и API используют savepoint, поэтому `commit()` приложения не мешает откату
всех тестовых данных после теста. Отели и комнаты загружаются из
`mock_hotels.json` и `mock_rooms.json`; остальные таблицы изначально пусты.
Создаваемые пользователи и удобства проверяются по фактическому ID, а не по
предположению, что последовательность всегда начинается с 1.

HTTP-клиент создаётся заново для каждого теста. Cookies и dependency overrides
не переходят между тестами. Кеширование остаётся включённым, но работает через
`InMemoryBackend` с уникальным префиксом. ASGITransport не запускает production
lifespan. Соединение с Redis отдельно проверяется на границе клиента, а
изображения и resize выполняются с настоящим Pillow во временных каталогах.
Отправка Celery-задачи подменяется только на границе `.delay()`.

Если процесс pytest принудительно завершить, его cleanup может не выполниться
и тестовая схема может остаться в БД. Её имя начинается с `pytest_`; перед
ручным удалением убедитесь, что она не принадлежит работающему запуску.
Запуск с pytest-xdist не входит в проверенную конфигурацию.

## Что проверяется

| Область | Проверки |
| --- | --- |
| Авторизация | Хеширование с солью, верный и неверный пароль, JWT payload/exp, cookie, вход/выход, закрытый профиль |
| Пользователи | Сохранение полей и хеша, отсутствие пароля в ответе, обязательные поля, email/sex/телефон, повторный email, удалённый пользователь |
| Отели | API и DB CRUD, частичное обновление, фильтры без учёта регистра, страницы, наличие доступных номеров |
| Комнаты | Получение и доступность по отелю, сохранение PUT/PATCH/DELETE, типы данных, удобства, изменение комнаты с чужим hotel_id |
| Удобства | API и DB CRUD/bulk, замена и удаление связей, дедупликация, FK-ограничения, каскадное удаление |
| Бронирования | Сохранённые даты/цена/пользователь, серверная цена, собственные брони, количество номеров, неизвестная комната, ошибки запроса |
| Доступность | Пересечения, вложенные и охватывающие интервалы, смежные даты, фильтр отеля, исчерпание quantity |
| Инфраструктура | Сессии DBManager, commit/закрытие при ошибках, Redis-коннектор, lifespan, Swagger/OpenAPI, изоляция фикстур |
| Изображения | Сохранение исходных байтов, очередь после записи, размеры/пропорции PNG/JPEG, повреждённые и отсутствующие файлы, обход пути |

## Известные ошибки приложения

`XFAIL` означает воспроизведённый дефект, а не успешную проверку приложения.
Все метки строгие: когда правильное поведение появится, pytest выдаст
`XPASS(strict)` с ненулевым кодом завершения, чтобы метку сняли.
Новый тип исключения также приводит к обычному FAIL.

В сценариях с несколькими проверками специальные исключения обозначают
только конкретный известный результат: `null` вместо списка, сохранённый
неверный интервал, необработанное переполнение или изменение удобств комнаты
через чужой отель. Проверки посторонних данных и других кодов ответа остаются
обычными assertions, поэтому новый дефект не должен становиться ожидаемым.

| Дефект | Где искать проверку |
| --- | --- |
| Неверный HTTPException для malformed JWT/другого ключа | `unit_tests/test_auth.py`, `integration_tests/test_auth.py` |
| Просроченный JWT не превращается в 401; не проверяются user_id и обязательный exp | Те же файлы |
| Удалённый пользователь приводит к ошибке response model | `integration_tests/test_auth.py` |
| Телефон проверяется после входной схемы; duplicate email даёт IntegrityError | `integration_tests/test_auth.py`, `unit_tests/test_schemas.py` |
| get_filtered не возвращает результат, /booking/me отвечает null | `bookings/test_booking_api.py`, `bookings/test_db.py`, `hotels/test_db.py` |
| BookingRepository задаёт schema вместо mapper | `bookings/test_db.py`, `bookings/test_booking_api.py` |
| Равные/обратные даты бронирования принимаются | `bookings/test_booking_api.py` |
| Исчерпание quantity вызывает bare Exception вместо HTTP 409 | `bookings/test_booking_api.py` |
| Выезд одной брони в день заезда следующей считается пересечением | `bookings/test_availability.py` |
| Hotel POST/PUT и room POST передают dict вместо схемы | `hotels/test_api.py`, `rooms/test_api.py` |
| Hotel PATCH вызывает commit у репозитория; room PATCH передаёт data дважды | Те же файлы |
| Hotel pagination не задаёт ORDER BY | `hotels/test_db.py` |
| Room PUT/PATCH/DELETE возвращают set вместо объекта status | `rooms/test_api.py` |
| Чужой hotel_id не защищает связи удобств комнаты от изменения | `rooms/test_api.py` |
| Upload допускает выход из каталога и произвольные байты; каталог должен заранее существовать | `unit_tests/test_images.py` |
| Resize очень узкого изображения получает высоту 0 | `unit_tests/test_tasks.py` |
| Задача сегодняшних заездов обращается к неверным именам DBManager/метода | `unit_tests/test_tasks.py` |
| Lifespan не закрывает Redis, если тело приложения выбрасывает исключение | `unit_tests/test_runtime.py` |

Предупреждения SQLAlchemy о Subquery и Pydantic о default HotelPatch сохранены
в выводе: их исправление требует изменения исходников приложения.

Реальные Redis, Celery broker/worker, SMTP, нагрузка и конкурентная гонка двух
бронирований последнего номера этим набором не проверяются. Интеграционные
тесты работают с таблицами ORM; Alembic upgrade/downgrade отдельно не запускался.
